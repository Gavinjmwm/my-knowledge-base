## 一、Redis 基础认知（面试开篇题）

> 高频程度：★★★

### 1. Redis 是什么？

Redis（Remote Dictionary Server）是一款开源的、基于内存的键值对数据库，支持多种数据结构，兼顾高性能与高可用，常用于缓存、会话存储、计数器、分布式锁等场景。

**核心优势**：高性能（单机 QPS 可达 10w+）、支持多种数据结构、支持持久化、支持集群、支持事务（弱事务）。

### 2. Redis 与 MySQL 的区别（必问）

> 高频程度：★★★★

| 对比维度 | Redis | MySQL |
| --- | :---: | :---: |
| 存储位置 | ==内存==（可持久化到磁盘） | 磁盘 |
| 读写速度 | 微秒级，单机 QPS 可达 10w+ | 毫秒级 |
| 数据结构 | 键值对，String / Hash / List / Set / ZSet 等 | 表（二维表格），结构化存储 |
| 查询能力 | 按 key 查询，不支持复杂 SQL | SQL 语言，多表关联、条件查询 |
| 事务 | 弱事务（不保证原子性、出错不回滚） | 强事务（ACID、可回滚） |
| 持久化 | RDB 快照 + AOF 日志，可能丢数据 | redo / binlog，数据可靠 |
| 扩展方式 | 主从、哨兵、Cluster 分片 | 主从复制、分库分表 |
| 定位 | 高速读写：缓存、计数器、分布式锁 | 持久存储：数据不能丢 |

**面试结论**：两者不是竞争关系，而是经典组合——MySQL 负责「永久保存」，Redis 负责「快速读写」。

## 二、Redis 五大数据结构

> 高频程度：★★★★

> [!IMPORTANT]
> 本节为补全内容：原文正文中此节缺失（仅在开篇提要中出现）。详细命令练习可对照本站《[Redis 基础](./redis-basics)》。

| 类型 | 底层实现 | 特点 | 典型场景 |
| --- | --- | --- | --- |
| String | SDS（简单动态字符串） | 最基础的「键 = 值」，可存字符串 / 整数 / 浮点数，也可把对象序列化成 JSON 整体存入 | 缓存、验证码、计数器（INCR） |
| Hash | ziplist / listpack → hashtable | 一个键下挂多个「字段-值」对，可单独读写某个字段，不必整体存取 | 存对象（用户信息、购物车） |
| List | ziplist → quicklist | 有序、可在头尾插入弹出 | 消息队列、最新动态、最新评论 |
| Set | intset → hashtable | 无序、自动去重，支持交 / 并 / 差集运算 | 抽奖、共同好友、标签去重 |
| ZSet（SortedSet） | ==跳表 + 哈希表== | 每个元素带 score 分数，按分数排序；哈希表保证单元素查询 O(1) | ==排行榜==、延迟队列、按分数范围查询 |

### 高频追问

1. **ZSet 为什么用跳表而不用平衡树？**
   跳表实现简单、范围查询高效（按 score 取区间就是跳表的一段遍历）；平衡树（如 AVL）插入删除要旋转、实现复杂。MySQL InnoDB 用 B+ 树是因为数据在磁盘、要减少磁盘 IO，而 Redis 数据在内存，跳表更合适。
2. **Hash / Set 什么时候升级编码？**
   当元素个数或单元素大小超过阈值（如 Hash 的 `hash-max-ziplist-entries` 默认 512）时，从压缩列表（ziplist/listpack）升级为哈希表（hashtable），以时间换空间。
3. **存对象用 String 还是 Hash？**
   如果对象需要频繁读写部分字段，用 Hash 更省流量、更灵活；如果永远整体读写，序列化成 String 存也可以。
4. **ZSet 里哈希表的作用是什么？**
   哈希表负责「成员 → score」的快速定位（O(1)），跳表负责排序和范围查询——两套结构配合，兼顾查询与排序（呼应下方「八、高频易错总结」）。

## 三、Redis 持久化机制：RDB vs AOF

| 对比维度 | RDB | AOF |
| --- | --- | --- |
| 数据一致性 | 差，可能丢失两次快照间的数据 | 高，最多丢失1秒（默认）或零丢失 |
| 文件体积 | 小 | 大 |
| 加载速度 | 快 | 慢 |
| 性能影响 | 小（bgsave 异步） | 稍大（写入命令有 IO 开销） |
| 适用场景 | 备份、灾难恢复、数据一致性要求低 | 数据一致性要求高、避免数据丢失 |

**面试结论**：生产环境推荐 RDB + AOF 结合使用，既保证数据一致性（AOF 负责），又兼顾备份和恢复效率（RDB 负责）；Redis 启动时，优先加载 AOF 文件（数据更完整），若 AOF 文件损坏，再加载 RDB 文件。

## 四、Redis 缓存三大问题（面试重中之重）

> 高频程度：★★★★★（必考大题，需掌握"问题定义+成因+解决方案"）

Redis 作为缓存使用时，最常出现三个问题：**缓存穿透、缓存击穿、缓存雪崩**，三者本质都是缓存未命中，导致请求穿透到数据库，引发数据库压力过大。

### 1. 缓存穿透

**（1）定义**

请求查询的数据既不在缓存中，也不在数据库中，导致所有请求都穿透到数据库，数据库持续承受高压力，甚至宕机。

例：查询不存在的用户 ID（如 id=-1），缓存和数据库都没有，恶意攻击者可利用此漏洞发起大量请求，攻击数据库。

**（2）解决方案（必背）**

1. **空值缓存**：查询数据库无结果时，将空值（或默认值）存入缓存，设置较短的过期时间（如5分钟），避免重复穿透；
2. **布隆过滤器**：提前将数据库中所有存在的 key 存入布隆过滤器，请求先经过布隆过滤器校验，不存在的 key 直接拒绝，不进入缓存和数据库；（最推荐，高效拦截）
3. **接口校验**：对请求参数进行校验（如用户 ID 不能为负数、不能超出合理范围），拦截非法请求。

### 2. 缓存击穿

**（1）定义**

请求查询的数据在数据库中存在，但不在缓存中（如缓存过期、缓存刚被删除），此时大量并发请求会穿透到数据库，导致数据库瞬间压力骤增。

例：热点商品缓存过期，此时大量用户同时查询该商品，所有请求都打到数据库。

**（2）解决方案（必背）**

- **热点数据永不过期**：对热点数据（如首页banner、热门商品）设置缓存永不过期，避免过期导致击穿；
- **互斥锁（分布式锁）**：缓存未命中时，只有一个请求能获取锁，去查询数据库并更新缓存，其他请求等待，避免并发穿透；（推荐，兼顾性能和一致性）
- **缓存预热**：系统启动时，提前将热点数据加载到缓存中，避免首次请求穿透；
- **过期时间错开**：对同类热点数据设置不同的过期时间，避免同时过期。

### 3. 缓存雪崩

**（1）定义**

大量缓存数据在同一时间过期，或 Redis 服务宕机，导致所有请求都穿透到数据库，数据库瞬间被压垮，引发系统雪崩。

例：电商大促时，大量商品缓存设置了相同的过期时间（如24小时），到期后同时失效，所有商品查询请求都打到数据库。

**（2）解决方案（必背）**

- **过期时间随机化**：对缓存数据的过期时间加上随机值（如 10-60秒），避免大量数据同时过期；
- **缓存集群**：部署 Redis 集群（主从+哨兵/Redis Cluster），避免单点故障，即使某个节点宕机，其他节点仍能提供服务；
- **热点数据永不过期**：核心热点数据设置永不过期，避免过期；
- **降级熔断**：Redis 宕机时，通过降级策略（如返回默认数据、提示系统繁忙），避免请求全部穿透到数据库；
- **限流**：对数据库请求进行限流，避免瞬间大量请求压垮数据库。

## 五、Redis 分布式锁（高频实操题）

> 高频程度：★★★★★

分布式锁是分布式系统中解决并发问题的核心方案，Redis 是实现分布式锁最常用的工具（比 Zookeeper 更轻量、性能更高），面试需掌握实现原理、问题及优化方案。

### 1. 分布式锁核心要求

- **互斥性**：同一时刻只有一个线程能获取锁；
- **安全性**：锁只能被持有锁的线程释放，不能被其他线程释放；
- **可用性**：锁获取和释放过程高效，避免死锁，即使 Redis 宕机，也能保证锁的正常使用；
- **可重入性**：同一线程可多次获取同一把锁（可选，根据场景需求）。

### 2. 基础实现（基于 SETNX 命令）

Redis 中 setnx 命令（set if not exists）：只有当 key 不存在时，才设置 value，返回1；若 key 已存在，返回0，天然满足互斥性。

**核心命令**：

- 获取锁：`setnx lock:key value`（value 建议用 UUID，保证唯一性，用于释放锁时校验）；
- 释放锁：先判断 value 是否为当前线程的 UUID，再执行 `del lock:key`（需原子操作，避免误删）；
- 设置过期时间：为锁设置过期时间（如 30秒），避免线程崩溃导致锁无法释放（死锁），命令：`expire lock:key 30`。

> [!WARNING]
> **问题**：setnx 和 expire 是两条命令，不是原子操作，若 setnx 执行成功后，Redis 宕机，expire 未执行，锁会变成永不过期，导致死锁。

### 3. 优化实现（原子命令 SET）

Redis 2.6.12 及以上版本，支持 set 命令原子化设置 key、value 和过期时间，解决上述问题：

核心命令（获取锁）：`set lock:key UUID NX EX 30`（NX=setnx，EX=设置过期时间，单位秒）；

释放锁：需通过 Lua 脚本实现原子操作（判断 value + 删除锁），避免误删其他线程的锁：

**Lua 脚本**：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

### 4. 进阶问题与优化（面试追问）

**（1）锁过期时间设置不合理？**

- 问题：锁过期时间太短，线程未执行完任务，锁已过期，导致其他线程获取锁，出现并发问题；
- 解决：实现锁续期（看门狗机制），线程持有锁期间，定期检查锁是否还在，若在则延长过期时间（如 Redisson 框架自带看门狗）。

**（2）Redis 单点故障？**

- 问题：Redis 单点宕机，锁无法获取和释放，导致分布式锁失效；
- 解决：部署 Redis 主从集群+哨兵模式，主节点宕机时，哨兵自动切换到从节点，保证锁服务可用。

**（3）可重入性问题？**

- 问题：同一线程多次获取同一把锁，会被拒绝（基础实现不支持可重入）；
- 解决：使用 Redisson 框架实现分布式锁，Redisson 自带可重入、看门狗、自动续期等功能，是生产环境首选。

### 5. 生产环境选型

**面试结论**：生产环境不建议手写 Redis 分布式锁，推荐使用 Redisson 框架，它封装了所有细节（原子性、可重入、看门狗、集群支持），开箱即用，避免手写出现漏洞。

## 六、Redis 集群原理（高阶考点）

> 高频程度：★★★★

单机 Redis 存在性能瓶颈（QPS 上限 10w+）和单点故障问题，生产环境需部署 Redis 集群，核心两种方案：主从复制+哨兵模式、Redis Cluster 集群。

### 1. 主从复制（基础集群）

**（1）原理**

一台主节点（master）+ 多台从节点（slave），主节点负责写操作，从节点负责读操作，主节点将数据同步到从节点，实现读写分离，提升并发能力。

**（2）数据同步流程**

1. 从节点启动时，向主节点发送 sync 命令，请求同步数据；
2. 主节点执行 bgsave 生成 RDB 快照，发送给从节点，从节点加载 RDB 文件，初始化数据；
3. 主节点将同步期间的写命令记录到缓冲区，同步完成后，将缓冲区的命令发送给从节点，从节点执行命令，保持与主节点数据一致；
4. 后续主节点执行写命令时，会实时将命令同步到从节点，保证主从数据一致。

**（3）优点与缺点**

- 优点：实现读写分离，提升读并发；主节点宕机后，可手动切换从节点为主节点，避免数据丢失；
- 缺点：不支持自动故障转移，主节点宕机后需手动切换，可用性低；不支持分片，所有数据都存在主节点，内存有限。

### 2. 哨兵模式（主从集群优化）

**（1）原理**

在主从复制基础上，增加哨兵节点（sentinel），哨兵节点负责监控主从节点的健康状态，当主节点宕机时，自动将一台从节点切换为主节点，实现自动故障转移，提升集群可用性。

**（2）核心功能**

- 监控：实时监控主从节点的运行状态；
- 故障转移：主节点宕机时，自动选举从节点为主节点；
- 通知：将故障转移结果通知给应用程序。

**（3）缺点**

仍不支持分片，所有数据都存在主节点，内存有限，无法应对海量数据存储需求。

### 3. Redis Cluster（分布式集群，生产首选）

**（1）原理**

Redis Cluster 是 Redis 官方提供的分布式集群方案，将数据分片存储到多个节点（主节点），每个主节点负责一部分数据（哈希槽），实现海量数据存储和高并发，同时支持主从复制和自动故障转移。

**（2）核心概念：哈希槽**

- Redis Cluster 将整个键空间分为 16384 个哈希槽，每个主节点负责一部分哈希槽（如 3个主节点，分别负责 0-5460、5461-10922、10923-16383 槽）；
- 数据存储时，Redis 对 key 进行哈希计算，得到哈希值，再映射到对应的哈希槽，将数据存储到该槽对应的主节点。

**（3）核心特点**

- 分片存储：数据分散到多个主节点，突破单机内存限制；
- 高可用：每个主节点对应多个从节点，主节点宕机时，自动切换从节点为主节点；
- 高并发：多个主节点同时处理读写请求，提升并发能力（QPS 可突破 10w+）；
- 去中心化：无中心节点，所有节点平等，可动态扩容、缩容。

## 七、Redis 其他高频考点

> 高频程度：★★★★

### 1. Redis 过期键删除策略（必问）

Redis 采用三种策略结合，平衡内存占用和性能：

- **惰性删除**：访问过期键时，才判断是否过期，过期则删除；优点：不消耗额外 CPU，缺点：过期键未被访问时，会占用内存（内存泄漏）；
- **定期删除**：每隔一段时间，随机抽取部分过期键进行删除；优点：平衡内存和性能，缺点：可能有少量过期键未被删除；
- **内存淘汰策略**：当 Redis 内存达到最大限制（maxmemory）时，触发内存淘汰，删除部分键（无论是否过期），释放内存。

### 2. Redis 内存淘汰策略（必问）

核心淘汰策略（面试重点记4种）：

- `volatile-lru`：淘汰过期键中最近最少使用的键；
- `allkeys-lru`：淘汰所有键中最近最少使用的键（生产常用）；
- `volatile-ttl`：淘汰过期键中剩余过期时间最短的键；
- `noeviction`：不淘汰任何键，内存满时拒绝写操作（默认策略，不推荐）。

### 3. Redis 事务（弱事务）

Redis 支持简单事务，通过 Multi、Exec、Discard 命令实现，但不保证原子性（单条命令原子，多条命令不原子）：

- `Multi`：开启事务，后续命令加入事务队列；
- `Exec`：执行事务队列中的所有命令；
- `Discard`：取消事务，清空队列；

> [!WARNING]
> 注意：事务执行过程中，若某条命令出错，其他命令仍会继续执行（不回滚），与 MySQL 事务不同。

### 4. Redis 为什么不支持事务回滚？

面试追问：Redis 作者认为，事务回滚会增加 Redis 的复杂性，且 Redis 命令出错多为编程错误（如类型错误），这类错误在开发阶段即可发现，无需在运行时回滚；同时，Redis 单条命令是原子的，足以满足大部分场景需求。

## 八、高频易错总结（面试避雷）

- Redis 快的核心是"内存操作+单线程+IO多路复用"，6.0 多线程仅优化 IO，核心逻辑仍单线程；
- ZSet 底层是跳表+哈希表，跳表负责排序，哈希表负责快速查询，是 Redis 最核心的高级数据结构；
- RDB 适合备份，AOF 适合数据一致性，生产环境推荐两者结合；
- 缓存穿透（查无数据）、击穿（热点数据过期）、雪崩（大量数据同时过期），解决方案需区分清楚，不可混淆；
- Redis 分布式锁需保证原子性，生产环境首选 Redisson 框架，避免手写；
- Redis Cluster 用哈希槽分片，16384 个槽，实现分布式存储，解决单机内存和并发瓶颈；
- Redis 事务是弱事务，不保证原子性，出错不会回滚；
- 内存淘汰策略中，allkeys-lru 是生产常用，noeviction 不推荐用于生产。
