## 一、短信登录：Redis 共享 Session

> 重要度：⭐⭐⭐（核心模式，先理解再记）

**问题来源**：传统 `HttpSession` 存在单机 Tomcat 内存里。集群部署时，用户第一次请求落到 Tomcat A，第二次被负载均衡打到 Tomcat B，B 上没有这个 session，登录态就丢了。

**替代方案要满足三点**：① 数据共享 ② 内存存储 ③ Key-Value 结构 → 天然指向 Redis。

**两个 Key 的设计（重点）**：

| 用途 | Key | Value |
| --- | :---: | :---: |
| 存验证码 | `phone:138xxxx` | 验证码（TTL 短，如 5 分钟） |
| 存登录用户 | `token:随机串` | 用户信息 JSON |

登录成功后返回 `token` 给客户端，客户端存到 localStorage / cookie，后续请求带上；拦截器从 Redis 查 token 拿用户。

> [!TIP]
> 用「随机 token 作 key」而不是「手机号作 key」存用户，是为了不让用户标识（手机号）暴露在前端，也更像标准方案。

**拦截器优化（双拦截器，黑马经典做法）**：
1. `LoginInterceptor`：拦截**需要登录**的路径，拿 token 查 Redis → 不存在则拦截；存在则存入 `ThreadLocal` 并**刷新 token 有效期**，放行。
2. `RefreshInterceptor`：拦截**所有**路径，只做「查 Redis + 存 ThreadLocal + 刷新有效期」，不拦截任何人。
   - 这么拆是为了：未登录用户访问公开页面时，也能刷新 token、且不会因为没 token 被拦死。

> [!WARNING]
> 登录用户信息存 Redis 时要设置 TTL，**每次访问都要续期**（刷新有效期），否则用户一直在线也会过期。这是「共享 Session」最容易忘的一点。

## 二、商户查询缓存：三大问题与一致性

> 重要度：⭐⭐⭐（本文最该背下来的部分）

### 2.1 缓存更新策略（三种）

| 策略 | 说明 | 一致性 | 维护成本 | 适用 |
| --- | :---: | :---: | :---: | :--- |
| 内存淘汰 | Redis 自己驱逐，不用人管 | 差 | 无 | 低一致性，如店铺类型 |
| 超时剔除 | 给缓存加 TTL，到期自动删 | 一般 | 低 | 通用兜底 |
| 主动更新 | 改数据库时同步改/删缓存 | 好 | 高 | 高一致性，如店铺详情 |

> [!TIP]
> 最佳实践：**高一致性需求 = 主动更新 + 超时剔除兜底**。超时剔除永远要留着，防止主动更新漏掉导致脏数据永远在缓存里。

### 2.2 Cache Aside Pattern（主动更新的标准姿势）

三个要决策的问题：

1. **删除缓存还是更新缓存？** → 选「**删除缓存**」。每次更新都写缓存会有大量无效写；删缓存、等查询时再重建更简单。
2. **先操作缓存还是先操作数据库？** → 选「**先更新数据库，再删除缓存**」。
   - 对比「先删缓存再更新库」：并发下线程 A 删缓存→线程 B 查缓存未命中→查库(旧值)→写回缓存(旧值)，导致缓存是脏数据。
   - 「先更新库再删缓存」在极端并发下也可能不一致，但概率极低，是业界默认选择。
3. **如何保证两步同时成功/失败？** → 单体系统放同一个事务；分布式用 TCC 等方案。

```text
读操作：缓存命中直接返回；未命中查库 → 写入缓存(带 TTL) → 返回
写操作：先写数据库，再删除缓存  （保证原子性）
```

> [!IMPORTANT]
> **面试一句话**：缓存与数据库一致性，用 Cache Aside——查询时回填缓存并设置 TTL，更新时先改库再删缓存，TTL 作兜底。

### 2.3 缓存穿透

> 重要度：⭐⭐⭐

**定义**：请求的数据在缓存和数据库里**都不存在**，于是缓存永远不命中，请求每次都打到数据库（恶意攻击 / 猜 id 时最常见）。

**解决方案**：

| 方案 | 优点 | 缺点 |
| --- | :--- | :--- |
| 缓存空对象（存 `null`，带短 TTL） | 实现简单 | 额外内存；短期不一致 |
| 布隆过滤器（请求先过 BF，不存在直接拒绝） | 内存占用极小 | 有误判率；实现复杂 |

> [!TIP]
> 还有几道「前置防线」：① 加强 id 复杂度，避免被猜 ② 做好基础格式校验 ③ 加强用户权限校验 ④ 热点参数限流。

### 2.4 缓存雪崩

> 重要度：⭐⭐⭐

**定义**：同一时段**大量 key 同时失效**，或 **Redis 直接宕机**，导致瞬间海量请求压到数据库。

**解决方案**：
- 给不同 key 的 TTL **加随机值**，错开失效时间 ⭐（最常用）
- 利用 Redis 集群提高可用性
- 缓存业务加**降级 / 限流**策略
- 业务加**多级缓存**（如本地 Caffeine + Redis）

### 2.5 缓存击穿（热点 Key 问题）

> 重要度：⭐⭐⭐

**定义**：一个被**高并发访问**且**缓存重建复杂**的 key 突然失效，瞬间所有请求同时去查库重建缓存，把数据库打崩。

**两种解法对比**：

| 方案 | 优点 | 缺点 |
| --- | :--- | :--- |
| 互斥锁（只放一个线程重建，其余等待重试） | 无额外内存；**保证一致性** | 线程等待，性能略降；有死锁风险（需超时） |
| 逻辑过期（value 里塞 expire 字段，不真过期，发现"过期"后开新线程重建，旧数据先返回） | 线程不等待，性能好 | **不保证一致性**；额外内存；实现复杂 |

> [!TIP]
> - 互斥锁思路：`SET lock NX` 抢锁 → 抢到查库重建；抢不到 sleep 后重试。
> - 逻辑过期思路：缓存**不设真 TTL**，数据里带逻辑过期时间；命中但逻辑过期时，抢到锁的线程开异步线程重建，当前请求先返回旧数据。
> - 选哪个？要强一致用互斥锁；要高性能、能容忍短暂旧数据用逻辑过期。

### 2.6 缓存工具类封装（四个方法，黑马作业）

> 重要度：⭐⭐（理解即可，代码照着写）

1. 任意对象 → JSON → 存 String（带 TTL）
2. 任意对象 → JSON → 存 String（带**逻辑过期**，用于击穿）
3. 查缓存 → 反序列化 → **缓存空值**解决穿透
4. 查缓存 → 反序列化 → **逻辑过期**解决击穿

> [!NOTE]
> 第 3、4 个方法的区别就在「未命中时怎么处理」：穿透版存 `null` 返回；击穿版发现逻辑过期就触发异步重建。

## 三、优惠券秒杀（思路）

> 重要度：⭐⭐（重点在锁，不在业务流程）

- **超卖问题**：多个请求同时判断"还有库存"再扣减，并发下会超卖 → 用数据库**乐观锁**（`WHERE stock > 0`）或 Lua 保证原子。
- **一人一单**：同一用户只能下一单 → 需要「用户 id + 优惠券 id」维度加锁。
- **分布式锁**：集群下 `synchronized` 失效，必须用 Redis 分布式锁（见第四节）。
- **异步秒杀**：用 Redis 预扣库存 + 消息队列（List / Stream）异步创建订单，削峰填谷。

## 四、分布式锁（Redis）

> 重要度：⭐⭐⭐（核心中的核心）

### 4.1 概念与要求

**定义**：满足**分布式 / 集群**下多进程之间「可见 + 互斥」的锁。

**好的分布式锁要满足**：互斥、安全性（不会误删别人的锁）、高可用、高性能。

**三种常见实现对比**：

| 实现 | 互斥原理 | 释放机制 | 评价 |
| --- | :--- | :--- | :--- |
| MySQL | 自带的锁机制 | 断开连接释放 | 性能一般 |
| Redis | `SETNX` 等互斥命令 | 锁超时时间到期释放 | 性能好、高可用 ⭐ |
| Zookeeper | 节点唯一性 / 有序性 | 临时节点断开自动释放 | 安全好，性能一般 |

### 4.2 手写 Redis 分布式锁

**获取锁（一步完成，原子）**：
```bash
# NX = 互斥（不存在才设），EX = 设置超时时间（防死锁）
SET lock thread1 NX EX 10
```
> 注意：**必须用 `SET NX EX` 一条命令**，不能用 `SETNX` + `EXPIRE` 两步——两步之间服务宕机会导致锁永远不释放（死锁）。

**释放锁**：
```bash
DEL lock
```
但**不能直接 DEL**！否则会删掉别人刚拿到的锁。必须「**先判断锁里的线程标识是不是自己，是才删**」。

**线程标识**：获取锁时存一个唯一标识（如 `UUID:线程id`），释放时比对。

**释放必须原子**：「判断标识 + 删除」两步要用 **Lua 脚本**包成原子操作（GET 比较 + DEL），否则并发下仍有误删风险。

### 4.3 手写版的四点不足

> 重要度：⭐⭐（知道有这些坑，引出 Redisson）

1. **不可重入**：同一线程不能多次获取同一把锁
2. **不可重试**：`tryLock` 只试一次就返回 false，没有等待重试
3. **超时释放隐患**：业务执行超过 TTL，锁提前释放，别的线程进来 → 不安全
4. **主从一致性**：主节点宕机、从节点还没同步到锁，锁就"丢失"了

### 4.4 Redisson（生产推荐）

> 重要度：⭐⭐⭐（直接用这个，别手写了）

Redisson 在 Redis 之上实现了 Java 分布式对象与服务，内置多种分布式锁。

**四大特性**（面试常问）：

| 特性 | 实现方式 |
| --- | :--- |
| 可重入 | 用 Hash 结构记录 `线程id → 重入次数` |
| 可重试 | 用信号量 + Pub/Sub 实现等待/唤醒重试 |
| 超时续约（watchDog） | 锁默认每隔 `leaseTime/3` 自动重置超时，业务没跑完也不会丢 |
| 高可用 | 支持 Redis 集群 |

**主从一致性问题（进阶）**：即使 Redisson，在「主从异步复制」下，主宕机而从未同步锁，仍可能丢锁。极端场景用 **RedLock（红锁，向多个独立 Redis 节点申请锁）**，但实现复杂、有争议，一般业务用 Redisson 默认即可。

```java
// 伪代码示意
RLock lock = redissonClient.getLock("order:" + userId);
boolean isLock = lock.tryLock();   // 可重试 + 看门狗续约
if (!isLock) { return; }
try {
    // 业务...
} finally {
    lock.unlock();                 // 可重入，安全释放
}
```
